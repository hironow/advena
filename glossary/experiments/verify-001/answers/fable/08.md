**結論: `sameRun` は破れます。**

`single` は `FENCE = false` なので、`check` は status を変えず、制作権も取りません。台本と音声のパスは常に世代 0 で、`publish` は何も確かめません。そのため、ack 期限切れによる再配信を別の実行が受けると、2 つの実行が同じパスに書き込めます。

反例の流れ (番組は `s1`、日付は 1 のまま):

1. `collect("s1", 0, true, false)`: status は creating、storedDay は 1、items は {1}、pending は true になる。
2. `deliver("s1", "r1")`: attempts は 1、r1 は started になる。
3. `check("r1")`: 終端でなく項目もあるので、r1 は selected になる。status は creating のまま。
4. `ackTimeout("r1")`: attempts 1 < 2 なので pending が true に戻り、r1 は orphan になるが実行は続く。
5. `deliver("s1", "r2")`: attempts は 2、r2 は started になる。
6. `check("r2")`: status はまだ creating なので、r2 も selected になる。
7. `writeScript("r1")`: scriptBlob(s1, 0) = r1。
8. `writeAudio("r1")`: audioBlob(s1, 0) = r1、r1 は voiced になる。
9. `writeScript("r2")`: scriptBlob(s1, 0) が r2 に上書きされる。
10. `publish("r1")`: 無条件に成功し、status は created になる。

最後の状態では status が created、pubSlot が 0 で、scriptBlob(s1, 0) = "r2"、audioBlob(s1, 0) = "r1" です。台本と音声を書いた実行が違うので、`sameRun` は偽になります。
