**結論: `sameRun` は `single` の到達可能なすべての状態で成り立ちます。** モデル検査は実行しておらず、仕様を読んだうえでの論証です。

理由は、公開されるスロットに書き込めるのが、その世代を取った 1 つの実行だけだからです。

1. **スロット 0 には誰も書かない。** `FENCE = true` なので `slotOf(e) = e.gen` です。書き込みは `pc` が `selected` 以降の実行だけが行い、そこに至るには `afterCheck` の FENCE 分岐で `gen = d.gen + 1 ≥ 1` を取る必要があります。

2. **世代は実行ごとに一意。** `docs.gen` を変えるのは `afterCheck` の FENCE 分岐 (+1) だけです。`collect` は `status == "none"` を要求し、status が `none` に戻る操作はないので、世代がリセットされることもありません。したがって世代 g (≥ 1) のスロットに書けるのは、その世代を取った 1 回の実行だけです。

3. **世代は範囲内に収まる。** 配信は高々 `MAX_ATTEMPTS = 2` 回 (`respond` は `attempts < 2` のときだけ再配信) なので、世代は 2 以下で `SLOTS = 0..2` をはみ出しません。

4. **公開の時点で台本と音声は同じ実行のもの。** 公開が成功するのは、`pc == "voiced"` の実行 r が `d.status == "producing"` かつ `d.gen == e.gen` を満たすときだけです。その時点で r は自分の世代 g のスロットに `writeScript` と `writeAudio` の両方を済ませており、他の実行はそのスロットに書けないので、`scriptBlob[(s, g)] == audioBlob[(s, g)] == r` です。

5. **公開後もそのスロットは変わらない。** 世代 g の実行は `publish` で `idle` に戻ります。公開後に `check` する実行は `TERMINALS` 分岐で `idle` になるので、新しい世代は生まれません。古い世代の実行がまだ動いていても、書く先は自分の世代のスロットで、その `publish` は `mayPublish` が偽になり `docs` を変えません。

`depFails`、`kill`、`ackTimeout`、`leaseExpires`、`midnight` と、項目 0 件の分岐 (`TERMINAL = false` なので status は変わらず、`lease` と `checkedNoItems` だけが変わる) は、いずれも `gen`、`pubSlot`、blob を変えないので、上の議論に影響しません。
