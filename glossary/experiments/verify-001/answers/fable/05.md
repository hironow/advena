**結論: 破れます (violated)。**

現行コード (`single` はスイッチがすべて false) では、台本と音声のパスの世代が常に 0 で、公開時に何も確かめません。そのため、ack 期限切れで再配信された 2 つ目の実行が、1 つ目の実行の公開後に同じパスへ上書きできます。

反例の流れ:

1. `collect("s1", 0, true, false)` — 文書が creating になり、項目は 1 日目にあり、配信待ちになる。
2. `deliver("s1", "r1")` — r1 が started になる (配信 1 回目)。
3. `ackTimeout("r1")` — 配信回数 1 < 2 なので再配信待ちになる。r1 は orphan になるが実行は続く。
4. `deliver("s1", "r2")` — r2 が started になる (配信 2 回目)。
5. `check("r1")` — status は creating で対象日 1 に項目があるので、r1 は selected になる。
6. `check("r2")` — まだ公開前なので、r2 も同じく selected になる。
7. `writeScript("r1")` — 台本パス (s1, 0) の内容が r1 になる。
8. `writeAudio("r1")` — 音声パス (s1, 0) の内容が r1 になる。
9. `publish("r1")` — status が created になり、pubScript と pubAudio はともに r1 と記録される。
10. `writeScript("r2")` — 台本パス (s1, 0) の内容が r2 に変わる。

最後の状態では status が created のまま、台本パスの内容 (r2) が pubScript (r1) と食い違うので、`unchangedAfterPublish` は偽です。
