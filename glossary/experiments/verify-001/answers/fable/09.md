`pair`(FIX_DAY = true, FENCE = false, TERMINAL = true, SWEEP = false)では `onePerDay` は成り立ちます。モデル検査は行わず、仕様を読んで論証した結論です。

1. **`storedDay` は必ず 1 以上で、作成後は変わらない。** FIX_DAY では `collect` が `storedDay = dayFor(arg, today)` を保存します。`arg` は 0 か `1..today` なので、値は必ず 1 以上です。`collect` は `status == "none"` のときだけ実行でき、他の操作は `storedDay` を書き換えず、`status` を `"none"` に戻す操作もありません。

2. **作成済みの番組どうしの `storedDay` は互いに異なる。** `collect` のガード `not(dayTaken(dayFor(arg, today)))` により、すでに `status != "none"` の番組が同じ `storedDay` を持つ場合は作成できません。1. と合わせると、この性質は以後も保たれます。

3. **公開された番組の `pubDay` は `storedDay` に等しい。** `status` が `"created"` になるのは `publishDoc` だけで、そこで `pubDay = runs.get(r).day` が入ります。実行の `day` は `afterCheck` で `targetOf(d, t)` として決まり、`storedDay != 0` なので `storedDay` そのものです(日付が変わっても影響しません)。実行の `doc` は `deliver` で決まったまま変わらないので、別の番組の日が混ざることもありません。

4. **したがって同じ日に公開済みの番組は高々 1 本。** `"created"` の番組が 2 本あれば、それぞれ `pubDay = storedDay` で、2. により値が異なります。

再配信・`ackTimeout`・`kill`・`depFails` による再実行は同じ番組を何度も制作・公開しうるだけで、`pubDay` は毎回同じ `storedDay` になるため、この不変条件には影響しません。
