# 所見と限界

## 全体の結論

- **現行コードは、業務の言明「1 日 1 回のみ」「新規出版がない日は提供されません」を、コードの上では守っていない。** 守る確認がなく、Scheduler と Eventarc の重複（どちらも公式文書が「起こりうる」と書く）で破れます。
- **重複配信と制作の中断に耐える 4 つの規則を、モデルの中で確かめた。** どの規則を外しても別の性質が破れます（[production-policy.md](production-policy.md)）。
- **最も大きい業務上の問題は、モデルからではなく、データの調査から出た。** 紹介する本を選ぶ `pubDate` は、NDL のデータでは発売日ではありませんでした（[business-gaps.md](business-gaps.md)）。
- **形式手法が加えたのは、主に「保証」です。** 対照実験の結論は下にあります。

## 用語集の形

- 用語はコードから起こし、コードにある用語にはすべて anchor を付けました。名前を変えたり消したりすると `just glossary check` が落ちます。
- 「コードがしていないこと」に頼る定義には、負の anchor（`!path#text`）を置きました。状態 `deleting` と `error` はフロントのコメントにあるだけで型には無いこと、Pub/Sub の購読に `--max-delivery-attempts` を指定していないこと、の 2 つです。誰かがそれを書き足すと、ゲートが落ちて定義の見直しを促します。
- 用語集は循環のない定義になっています（Lean の `terms_wellFormed`）。

## 状態 creating の多義性

- creating は、配信待ち、制作中、該当なしで終わった、配信が打ち切られた、の 4 つの状況を兼ねます。
- 前の 2 つはまだ進み、後の 2 つは二度と進みません。status だけでこれを見分ける関数は存在しない、と Lean で証明しました（`creating_is_overloaded`）。
- 証明は「status の写しと、コードを読んで分けた 5 つの状況」についてのものです。分け方が正しいかは、コードを読んだ私の判断です。

## 番組対象日

- broadcasted_at の無い番組は、制作を始めた時刻の JST 日付で本を選びます（`workflows.py` の `exec_date_jst`）。同じ文書でも、制作する日が違えば番組対象日が変わることを Lean で示しました（`day_depends_on_production_time`）。
- モデルでは、制作が中断して再配信が 0 時をまたぐと、翌日の日付の項目が翌日の番組として公開されます（`lateProductionTest`）。結合マスタデータには翌日の日付の項目も入りうるので（`split_books` の「未来」）、この場面は到達できます。

## 番組制作（停止の場面）

外部の確認は Eventarc の文書作成イベント、停止は制作の中断です。現行コード、方針案、方針案から 1 つずつ規則を除いたものを比べました。表は [production-policy.md](production-policy.md) にあります。

現行コードで見つかった反例（scripted run で手順を固定したもの）:

| 反例 | 手順 | scripted run |
|---|---|---|
| 同じ日に 2 本 | 収集実行が 2 回動き、どちらも公開される | `code2.twoShowsOneDayTest` |
| 台本と音声の混線 | r1 が台本を書く → ack 期限切れ → 再配信を r2 が受けて台本を上書き → r1 が音声を書いて公開 | `code1.mixedScriptAndAudioTest` |
| 該当なしで止まる | 0 件 → 204 → 配信は終わり、番組は creating のまま | `code1.noItemsLeavesCreatingTest` |
| 配信打ち切りで止まる | 依存先の失敗が再配信の上限まで続く → dead letter、番組は creating のまま | `code1.haltUntilDeadLetterTest` |
| 翌日の番組になる | 中断 → 0 時 → 再配信 → 翌日の項目で公開 | `code1.lateProductionTest` |

- 台本と音声の混線には、再配信を別のインスタンスが受けることが要ります。backend は uvicorn の 1 プロセスで、制作中はイベントループを止めるので、同じインスタンスに届いた再配信は前の制作の後に回ります。Cloud Run の台数の設定はリポジトリにないので、起こりうるかは本番の設定によります。
- 方針案でも、同じ番組を 2 つの実行が同時に制作することは残ります（`proposal1.oneProducerAtATime`）。費用の問題として業務への質問にしました。

### 方針案を作る途中で見つけた誤り

回収処理の最初の版は、配信を受けた実行が status を確かめる前に、番組を failed にしてしまいました。TLC が反例を返したので、「その番組を扱う実行もない」を条件に足しました。
同じ時に「failed は本来の日に項目があった番組だけ」という性質も破れました。これは性質の方が強すぎたので、「該当なしと確かめた番組は failed にならない」に言い直しました。

## 利用者文書

- 同じ人の 2 つの初回サインインで、利用者文書が 2 つできるかは、Firestore のトランザクションが「該当なし」という検索結果を守るかで決まります（`accountUnguarded` で V、`accountGuarded` で H）。
- Firestore は直列化可能な分離を保証すると書いていますが、空の検索結果を守る仕組みは書いていません。

## 対照実験

### verify-001: 変種が性質を守るかを、道具なしで判定できるか

**道具を持たない 3 つのモデル（Fable 5.2、Opus 5.5、Sonnet 5.5）が、12 問すべてに正解した。形式手法が加えたのは「保証」で、「発見」ではない。**

- 番組制作のモデルの 4 つのスイッチの全 16 変種について、TLC で正解表を作り、乱数で 12 問（成り立つ 6、破れる 6）を選んだ。
- 「破れる」と答えた 18 件の反例は、すべて Quint で再生でき、性質が実際に破れた。
- 予想（Sonnet は 9〜10 問）は外れた。予想した誤りの集まり方も、誤りが無かったので確かめられない。
- だから、この用語集のどの主張も「形式手法が見つけた」とは書かない。「TLC が到達できる全状態で確かめた」と書く。
- 調べていないこと: 大きなモデル、時相性質、方針案の条項や質問を対照が自分で思いつけるか（発見の実験）。

## 限界

- **モデルの大きさ**: JST の日付 2 日、番組 1〜2 つ、制作実行の枠 1〜2 つ、再配信 2 回まで（Pub/Sub の既定は 5 回）。大きくして結論が変わらないかは確かめていません。
- **モデルが省いたもの**: Firestore と GCS の失敗、`update_in_transaction` による移行の書き込み、LLM の再試行（tenacity、最大 3 回）、NG ワードの除外、`/add_user` の Eventarc 配信、Cloud Run の CPU の割り当て（リクエストの外では止まりうる）。
- **確かめていない性質**: 費用の上限、制作にかかる時間、聴取者が実際に見るもの。
- **実装との対応**: 反例はコードのモデルに対するもので、実装では再現していません。再現するなら、Firebase Emulator の上で、上の表の手順どおりに `/add_radio_show` を 2 つのプロセスから呼び、`publish` の直前で片方を止める必要があります。
- **設定値**: ack 期限 300 秒、再配信の間隔 300〜600 秒は `scripts/` の値です。本番の設定は確かめていません。
- **調査の確かさ**: 一次資料で確かめた点と二次情報は [business-gaps.md](business-gaps.md) で分けています。
- **レビュー**: 業務を知る人のレビューは受けていません。
